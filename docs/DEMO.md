# Демонстрация TapTuna

Все шаги — через GUI

## Подготовка (за день до защиты)

1. Убедиться, что установлен `tshark`:
   ```bash
   tshark -v | head -1
   ```

2. Скачать `TapTuna-0.1.0-x86_64.AppImage` из релиза GitHub.

3. **Очистить тестовые проекты** — демонстрация с чистого листа:
   ```bash
   rm -rf ~/TapTuna/projects ~/TapTuna/projects.json
   ```

4. Заранее положить в `~/Downloads/`:
   - `sensor_demo.pcap` — реальный TCP-трафик (можно взять из
     `examples/demo_project/captures/` или сгенерировать через
     `python -m taptuna.examples.generate`).
   - `04_expression.yaml` — пример интерпретации из
     `examples/interpretations/`.

5. **Прогнать демонстрацию целиком один раз** — убедиться, что не
   ломается ни на одном шаге.

---

## Демонстрация

### Шаг 0. Запуск (30 сек)

Двойной клик по `TapTuna-0.1.0-x86_64.AppImage`.

> **Что сказать:** «Приложение полностью локальное, работает офлайн,
> данные хранятся в `~/TapTuna/`. Открывается окно со списком
> проектов. Если `tshark` не установлен — приложение покажет экран
> с инструкцией, а не упадёт с ошибкой».

### Шаг 1. Импорт PCAP и автоименование (2 мин)

- `/welcome` → в поле **«Путь на сервере»** ввести
  `~/Downloads/sensor_demo.pcap`.
- Нажать **«Импортировать»**.
- Прогресс в правом нижнем углу.
- Дождаться toast «Ingest завершён».

> **Что сказать:** «Импорт запускается фоновым job'ом, прогресс виден
> в панели задач. Проект автоматически создаётся с именем из PCAP —
> `sensor_demo`. Если в текущем проекте уже есть captures — создастся
> **новый** проект. Это ускоряет работу: не нужно вручную придумывать
> имена».

**Альтернатива:** перетащить `.pcap` в окно drag-n-drop — тот же результат.

### Шаг 2. Обзор сессий (1 мин)

- **Сессии** в навигации сверху.
- Показать список: N сессий, IP-адреса, порты, размеры.

> **Что сказать:** «Сессия — это TCP-соединение. Для каждой видны
> количество пакетов и байт в каждом направлении. Проект может
> содержать сотни сессий».

### Шаг 3. Возврат к байтам источника (2 мин)

- Кликнуть по **ID любой сессии** → откроется `/sessions/<id>`.
- Показать hex-viewer.
- **Кликнуть по байту** → всплывёт popup с `frame`, `seq`, `flags`.

> **Что сказать:** «Ключевое свойство: любой байт потока ссылается
> на конкретный кадр в исходном PCAP. Если пользователь видит
> странное значение поля, он кликает и смотрит, из какого пакета
> оно пришло. Это требование ТЗ — результат анализа должен быть
> связан с источником».

### Шаг 4. Исследование: поиск, сравнение, framing (4 мин)

- **Исследование** в навигации.
- Выбрать сессию → **«Загрузить»**.
- Показать **два hex-viewer'а** (a_to_b и b_to_a).
- В **Поиске** ввести `48656c6c6f` (hex «Hello») → подсветка.
- Раздел **«Framing tool»**: выбрать `fixed`, size=13 → **«Применить»**.
- Показать таблицу: сколько сообщений, hex-заголовки.
- Кнопка **«Показать границы в hex»** — границы подсвечиваются
  в hex-viewer.

> **Что сказать:** «Framing tool помогает найти границы сообщений
> прямо в интерфейсе. Не нужно писать код — выбираем стратегию,
> смотрим результат визуально. Кнопка «к байтам» перепрыгивает
> к нужному offset».

### Шаг 5. Создание интерпретации (3 мин)

- **Интерпретации** в навигации.
- Вкладка **YAML** → вставить содержимое `04_expression.yaml`.
- **«Добавить»** → создана `demo_expression@v1`.
- Переключиться на вкладку **«Форма»** — показать визуальный редактор.
- Показать **Preview** на сессии: что извлекается.

> **Что сказать:** «Интерпретация декларативная: framing + fields +
> constraints. Не требует программирования. Для сложных случаев
> есть script-интерпретации с Python-песочницей: RLIMIT_CPU,
> RLIMIT_AS, whitelist импортов. Но в 90% случаев хватает
> декларативного подхода».

### Шаг 6. Verify на корпусе (3 мин)

- **Проверка** в навигации.
- Создать корпус:
  - имя: `demo_corpus`
  - критерии: `{"any_ports": [8080], "min_packets": 1}`
- **«Добавить корпус»**.
- Запустить verify:
  - корпус: `demo_corpus`
  - интерпретация: `demo_expression@v1`
  - **«Запустить»**.
- Дождаться завершения (прогресс в панели задач).
- **«Результаты»**.

> **Что сказать:** «Verify прогоняет интерпретацию по всему корпусу
> и классифицирует каждое сообщение:
> **ok** / **violation** / **ambiguous** / **incomplete** /
> **not_applicable**. Verdict — самый тяжёлый из встреченных
> статусов. У каждого результата есть ссылка «→ байты» на источник».

- Если есть `violation` — кликнуть «→ байты» → вернуться к пакету.

### Шаг 7. Гипотезы (4 мин)

- **Исследование** → прокрутить вниз до «Гипотезы и наблюдения».
- Раскрыть справку **📖 Как работать с гипотезами**.
- Ввести гипотезу:
  - **Формулировка:** `magic всегда 0x48`
  - **Выражение:** `magic == 0x48`
  - **Интерпретация:** `demo_expression@v1`
- **«Добавить гипотезу»**.
- Нажать **«Проверить»** → дождаться.
- **«Результаты»** → показать satisfied / violated / not_applicable.
- Кликнуть на **violated** → **«→ байты»** → переход к кадру.

> **Что сказать:** «Гипотеза — это предположение о смысле данных.
> В отличие от constraints (правил разбора), гипотеза проверяется
> **отдельно** и не влияет на статусы verify. Автоматический статус:
> **supported** / **refuted** / **inconclusive**. Каждый контрпример
> связан с конкретными байтами. Успешная проверка структуры сама
> по себе не подтверждает смысловую гипотезу — это важно».

- Добавить вторую гипотезу `exists(payload)` для демонстрации
  другого типа.

### Шаг 8. Отчёт (2 мин)

- **Отчёт** в навигации.
- Выбрать последний run → **«Сгенерировать»** (все три формата).
- Открыть `.md` — показать разделы:
  - §1 Цели и границы
  - §2 Метод (tshark, политика overlap, checksum)
  - §4 Проверенные примеры
  - §5 Контрпримеры
  - §6 Неизвестные участки
  - §9 Гипотезы и наблюдения (отдельно от правил)
- Открыть `.machine_model.json`.

> **Что сказать:** «Markdown — источник истины. Из него генерируется
> HTML. И `machine_model.json` — самодостаточная интерпретация:
> framing + fields + constraints без привязки к TapTuna. Её можно
> применить на других данных или передать в другой движок. Это
> требование ТЗ: воспроизводимость и повторное применение».

### Шаг 9. Экспорт и импорт проекта (1 мин)

- **Проекты** (⇄ иконка в навигации) или на главной.
- У `sensor_demo` нажать **«↓ Экспорт»** → скачается
  `sensor_demo.taptuna.zip`.
- **«📂 Выбрать файл…»** → выбрать скачанный zip → **«Импортировать»**.
- Создастся `sensor_demo_2` (уникализация имён).

> **Что сказать:** «Проект целиком передаётся одним архивом: PCAP,
> интерпретации, корпуса, наблюдения, гипотезы, отчёты. Другой
> инженер откроет его и получит всю картину исследования. Не нужно
> повторно настраивать окружение».

### Шаг 10. Закрытие (30 сек)

> **Что сказать:** «Ключевое отличие от Wireshark: не просмотр
> пакетов, а проверяемая интерпретация протокола с сохранением
> оснований выводов. Инструмент работает офлайн, не требует
> серверов, передаётся одним файлом».
