# Методология исследования протокола

Документ описывает подход, который реализует TapTuna (§8 ТЗ МАДРИГАЛ).

## 1. Общая схема

```
PCAP → Reassembly → Исследование → Гипотеза → Интерпретация → Верификация → Отчёт
         │              │             │              │              │           │
    источник      framing-tool     наблюдения    declarative/    корпус +    MD+HTML+
    неизменен     + поиск          + гипотезы     script         5 статусов  model.json
```

На каждом шаге сохраняется **происхождение**: любой результат ссылается
на session_id, direction_id, stream_offset, frame_number.

## 2. Этап 1: восстановление потока

**Что делаем.** TCP — байтовый поток, а не последовательность пакетов.
Прикладное сообщение может пересекать границы TCP-пакетов; один пакет
может содержать несколько сообщений.

**Как.** Reassembly по RFC 9293:

- Sequence numbers сравниваются как серийные числа (±2³¹).
- Одинаковые повторные передачи дедуплицируются (по совпадению seq,
  длины и данных).
- Пропуски (seq не пришёл) → **gaps**, не заполняются нулями.
- Перекрытия с разными данными → **ambiguities**, политика
  (`first_wins`, `last_wins`, `halt_and_mark`) видна и воспроизводима.

**Что видно пользователю.** В hex-viewer'е: gaps — красным, ambiguities —
жёлтым. В таблице пакетов — frame_number, seq, offset.

## 3. Этап 2: исследование границ

**Проблема.** Неизвестно, где кончается одно сообщение и начинается
следующее. Границы не совпадают с границами пакетов.

**Направления поиска:**

1. **Фиксированный размер.** Если все сообщения одинаковой длины —
   стратегия `fixed`.
2. **Префикс длины.** Если первые байты сообщения кодируют его длину
   (`length_prefix`, LE/BE, включает ли префикс себя).
3. **Разделитель.** Если между сообщениями стоит маркер (CRLF, NUL,
   специфический байт) — `delimiter`.
4. **Regex.** Если границу можно выразить шаблоном — `regex`.

**Инструмент:** Framing tool на `/research`. Выбираем стратегию и
параметры, сразу видим разбиение. Клик «к байтам» прыгает к offset
в hex-viewer'е.

**Признаки верной гипотезы:**

- Все сообщения одинаковой структуры (например, первое поле — `magic`).
- Нет «лишних» leftover'ов, кроме осмысленных.
- На **другой** сессии с тем же протоколом — то же разбиение.

## 4. Этап 3: гипотезы о полях

**Проблема.** Даже зная границы, непонятно, что означают поля.

**Направления поиска:**

1. **Diff двух сообщений.** Side-by-side в `/research`: общий префикс,
   суффикс, различия в середине. Совпадающие байты — вероятно,
   фиксированные (magic, версия). Различающиеся — данные.
2. **Корреляция с действиями.** Журнал действий: после «задать 21»
   в потоке появляется значение 21. Это повод для гипотезы.
3. **Корреляция с параметрами.** Разные действия → разные значения
   поля. Проверяем: если меняем параметр 21→42, меняется ли конкретное
   поле 21→42?

**Инструмент:** `/research` + `/action-log`. Оверлей действий на сессии,
сравнение двух сессий.

**Форма гипотезы.** Запись в таблице `hypotheses`:

```
formulation: "Поле offset=4 в команде set_mode содержит 32-битное LE-число"
status: open | supported | refuted | superseded
```

Гипотеза связывается с наблюдениями (`hypothesis_observations`).

## 5. Этап 4: интерпретация

**Что делаем.** Превращаем гипотезу в **применяемое правило**.

**Форма:**

- **Declarative** — YAML с полями `framing`, `fields`, `constraints`,
  `semantics`. Применяется движком без программирования.
- **Script** — Python-функция `interpret(payload, index, stream_offset)`
  в sandbox (RLIMIT_CPU/AS, whitelist импортов, timeout).

**Важно:** интерпретация **версионируется** (`name@vN`). Изменение
создаёт новую версию; старые прогоны не удаляются, а помечаются `stale`.

**Связь гипотеза ↔ правило.** Гипотеза говорит «предположительно, это
длина». Правило говорит «извлеки u16be из offset 2». Если гипотеза
опровергнута, правило пересматривается — но байты источника не меняются.

## 6. Этап 5: верификация

**Что делаем.** Прогоняем интерпретацию по **корпусу** (набору записей).

**Классификация каждого сообщения:**

| Статус | Что значит |
|---|---|
| `ok` | Все поля извлечены, constraints выполнены |
| `violation` | Constraints не выполнены (правило нарушено) |
| `ambiguous` | Сообщение попало в область перекрытия с конфликтом |
| `incomplete` | Не удалось извлечь все поля, есть неизвестные диапазоны |
| `not_applicable` | Сообщение не относится к данной интерпретации |

**Вердикт прогона:** самый «тяжёлый» из встреченных:
`violation > ambiguous > incomplete > ok > not_applicable`.

**Важно:** успешный разбор структуры **не подтверждает** смысловую
интерпретацию. Отчёт отделяет:

- **rule-based** — результат движка (`verification_results`);
- **гипотезы** — предположения о смысле (`hypotheses`).

## 7. Этап 6: уточнение

**Что делаем.** Находим контрпримеры — данные, где правило не работает.

**Как ищем:**

1. Фильтр результатов по `status=violation` в `/verification`.
2. Клик на результат → переход к сессии/offset.
3. В `/research` исследуем: что отличается в этом примере?
4. Обновляем интерпретацию → создаём `name@vN+1`.
5. Повторная верификация на том же корпусе → сравнение сводок.

**Итерация:** пока verdict не станет `ok` или пока не решим, что
оставшиеся нарушения — не ошибка правила, а реальное поведение
устройства (тогда фиксируем в разделе «Область применимости»).

## 8. Этап 7: отчёт

**Что фиксируем (§11.1 ТЗ):**

1. Цели и границы.
2. Метод (команды tshark, политики overlap/checksum).
3. Корпус (sha256 записей, критерии отбора).
4. Проверенные примеры (status=ok).
5. Контрпримеры (violation, ambiguous).
6. Неизвестные участки (incomplete, unknown_frame).
7. Область применимости.
8. Открытые вопросы.
9. Гипотезы (отдельно от rules).
10. Предупреждение о checksum offloading.

**Форма:**

- Markdown — source of truth.
- HTML — для чтения.
- `machine_model.json` — воспроизводимая модель, применимая к новым
  данным без TapTuna.

## 9. Принципы, которые нельзя нарушать

1. **Источник неизменен.** PCAP копируется по sha256, оригинал не трогаем.
2. **Неизвестное не подменяется.** Пропуски — gaps, не нули. Неуверенные
   данные — incomplete, а не «ok с догадкой».
3. **Правило отделено от гипотезы.** Результат движка — не утверждение
   о назначении поля.
4. **Версионирование.** Изменение интерпретации → новая версия, старые
   результаты помечены `stale`.
5. **Воспроизводимость.** Одинаковые PCAP + интерпретация + seed +
   политики → идентичный `run_hash`.
6. **Переход к источнику.** Любой результат → offset в потоке → frame.

## 10. Ограничения метода

- Только TCP/IPv4 поверх Ethernet.
- Один интерфейс, одна точка захвата.
- Не поддерживается автоматическое построение полного автомата состояний.
- Гипотезы о смысле полей не проверяются автоматически — только через
  анализ контрпримеров человеком.
