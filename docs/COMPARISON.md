# Обоснование стека

Документ объясняет, почему выбраны Rust + PyO3 + Flask + SQLite, и как
это помогает решать задачи исследования (§11 ТЗ МАДРИГАЛ).

## 1. Почему Rust для ядра

Задача ядра — работа с байтами: парсинг wire, reassembly, framing,
extract, safe-eval. Требования §12.7: **100 МиБ потоков за ≤ 90 секунд**
и профиль §10: **100k сообщений, 1000 сессий**.

**Вариант «чистый Python»** для reassembly 100 МиБ:

- Тип `bytes` в Python — 1 байт/элемент, но любая операция над ним
  (склейка, поиск, сравнение) создаёт копии.
- `bytearray` быстрее, но требует ручного управления длиной.
- 100k сообщений через `bytes` — десятки секунд на framing+extract.
- GIL ограничивает параллелизм.

Оценка: 100 МиБ reassembly на чистом Python — 30–60 секунд. Укладывается
в 90 секунд, но **пиковая память** может дать ×50–100 от входа
(промежуточные list[int], большие копии), что уводит за бюджет §10.

**Вариант «Rust»:**

- `Vec<u8>` — фиксированные 1 байт/элемент.
- Склейка через `extend_from_slice` — memcpy.
- Zero-copy парсинг: байты читаются из slice без копий.
- Обработка 100 МиБ: **46.8 ms** (2 GiB/s).
- Пиковая память: **290.7 MiB** (×2.9 от входа).

Разница в **12 раз по скорости** и **10 раз по памяти**. Оба требования
§12.7 и §10 закрыты с запасом.

## 2. Почему PyO3, а не subprocess или FFI

**Вариант «subprocess с Rust-бинарником»:**

- Обмен через stdin/stdout — сериализация/десериализация на каждом вызове.
- Rust-бинарник не имеет доступа к SQLite-контексту.
- Сложнее распространять: один wheel вместо двух артефактов.
- Нельзя вызвать Python-callback'и (для progress-баров, SSE).

**Вариант «C FFI»:**

- Ручное управление памятью, ошибки сегфолтят.
- Нет автоматической конвертации типов (list[int] → Vec<u8>).
- Нет `abi3` — wheel привязан к конкретной версии Python.
- Много шаблонного кода для bindings.

**PyO3:**

- Автоматическая конвертация типов: Python `bytes` ↔ Rust `Vec<u8>`.
- `abi3-py311` — **один wheel работает на Python 3.11, 3.12, 3.13, 3.14**.
- Обработка ошибок через `PyResult<T>` — никаких сегфолтов.
- Прямой вызов native-функций из Python без сериализации.
- `maturin` собирает wheel одной командой.

**Цена:** Rust-toolchain нужен только для сборки. Пользователь получает
готовый wheel через `pip install`, без Rust.

**Fallback:** если native не собран, `taptuna.native` автоматически
переходит на чистую Python-реализацию (`fallback.py`). Функциональность
сохраняется, скорость падает в 10–20 раз. Управление через `TAPTUNA_NATIVE=0`.

## 3. Почему Flask, а не FastAPI или Django

**Требование §11:** «Настольный интерфейс либо веб-приложение на localhost».

**Django** — избыточен. ORM, миграции, admin — не нужны. SQLite-схема
управляется вручную (14 таблиц, `PRAGMA user_version`).

**FastAPI** — современный, но:

- Async-first архитектура. Наши долгие операции (ingest, verify) —
  CPU-bound в Rust, async не даёт преимуществ.
- Требует `uvicorn` как ASGI-сервер.
- SSE через `StreamingResponse` работает, но менее прямолинейно.

**Flask:**

- Простой синхронный WSGI. Работает из коробки на localhost.
- Blueprint-система — API и UI разделены чисто.
- SSE через `Response(generator, mimetype="text/event-stream")` — 5 строк.
- Jinja2 встроен — для 9 HTML-шаблонов.
- Никаких дополнительных зависимостей.

**Цена:** нет async. Но у нас и нет async-задач: долгие операции идут в
фоновых потоках (`jobs.py`), прогресс — через SSE.

## 4. Почему SQLite, а не PostgreSQL или файлы

**Требование §14:** 14 таблиц, индексы, миграции, `PRAGMA user_version`.

**PostgreSQL** — сервер БД на localhost. Оверхед для одиночного
пользователя. Установка, конфигурация, порт — всё это лишнее.

**Файлы** (JSON, YAML):

- Нет транзакций — при падении процесса данные теряются.
- Нет индексов — поиск по `frame_number` = полный скан.
- Нет foreign keys — целостность вручную.
- Сложно делать сводки (`SELECT COUNT(*) GROUP BY status`).

**SQLite:**

- Один файл `project.sqlite` — переносится вместе с проектом.
- ACID-транзакции.
- Индексы (`idx_vres_run_status`, `idx_seg_dir_offset`, ...) — быстрый
  поиск результатов verify.
- `ON DELETE CASCADE` — целостность.
- `PRAGMA user_version` — версионирование схемы.
- Нет сервера, нет сети, нет установки.

**Цена:** один писатель за раз. Для localhost-UI это не проблема: ingest
пишет один поток, UI читает.

## 5. Почему tshark, а не свой парсер PCAP

**Требование §6.2:** «один вызов tshark на файл, `-T fields`, `occurrence=f`».

**Свой парсер PCAP** на Rust:

- PCAP/PCAPNG — сложные форматы. PCAPNG — блоки с опциями, interface
  description, timestamp resolution.
- Нужно реализовать разбор Ethernet/IP/TCP с VLAN, TCP-опциями, флагами.
- Нужно регулярно обновлять под новые версии Wireshark и его preferences.
- Риск расхождения с тем, что видит пользователь в Wireshark.

**tshark:**

- Эталонный парсер Wireshark. То, что видит пользователь, — то и в ingest.
- `-T fields` даёт машинно-читаемый TSV.
- Поддерживает VLAN, IPv6, TCP-опции «бесплатно».
- Версия фиксируется в `manifest.json` — воспроизводимость.
- Правило «один вызов на файл» соблюдается — никаких `-Y tcp.stream==N`.

**Цена:** tshark — внешняя зависимость. Установка через
`apt/brew/pacman`. Проверка версии при первом запуске.

**Fallback:** если tshark не найден, `TAPTUNA_TSHARK` или `PATH` не
содержат его — ошибка `TSHARK_NOT_FOUND` с явным сообщением.

## 6. Почему декларативная модель + script, а не только один из них

**Требование §7.1 R3:** «декларативная модель, скрипт, набор правил,
результат алгоритма или их сочетание».

**Только declarative (YAML):**

- Простые протоколы описываются за 10 строк.
- Не требует программирования.
- Воспроизводится в `machine_model.json` без TapTuna.

Но: сложные зависимости (поле X зависит от длины поля Y, вычисленной
из Z) выразить сложно.

**Только script (Python):**

- Любая логика.
- Но: требует написания кода, менее безопасно, не переносится в JSON.

**Оба:**

- Declarative — для 80% случаев (фиксированные поля, length-prefix,
  простые constraints).
- Script — для сложной логики, с sandbox (RLIMIT_CPU/AS, whitelist
  импортов, timeout).
- Модель в `machine_model.json` всегда декларативная. Script может
  конвертироваться в декларативный, если логика простая.

## 7. Почему SQLite-схема из 14 таблиц, а не 3–4

**Минимум:** captures, sessions, packets. Хватило бы для отображения.

**Но требование §6:** «Производный результат связан с конкретным
источником и соответствующим диапазоном данных».

14 таблиц — это:

- `captures` — источник (sha256, tshark версия).
- `sessions`, `directions`, `stream_segments`, `packets` — уровень байтов.
- `interpretations` — версионированное правило.
- `corpora`, `verification_runs`, `verification_results` — верификация.
- `observations`, `hypotheses`, `hypothesis_observations` — гипотезы
  и их основания.
- `action_log` — журнал действий.
- `meta` — служебное.

Разделение позволяет:

- Пересчитать verify без повторного ingest.
- Помечать stale результаты отдельно.
- Хранить гипотезы отдельно от rule-based результатов (§9 ТЗ: «Правило
  отделено от гипотезы»).

## 9. Что бы мы изменили при других требованиях

- **Если бы требовался GUI, а не веб:** Tauri (Rust + web frontend) вместо
  Flask. Тот же Rust-ядро, но без Python-слоя.
- **Если бы требовалась многопользовательская работа:** PostgreSQL вместо
  SQLite, FastAPI вместо Flask, очереди (Celery/RQ) для долгих операций.
- **Если бы требовалась потоковая обработка:** замена `tshark -T fields`
  на live capture через `dumpcap` + потоковый reassembly.
- **Если бы требовался IPv6 и IP-фрагментация:** расширение `wire.rs`
  на дополнительные протоколы.

Все эти изменения не потребуют переписывания ядра — только замену
верхнего слоя.
